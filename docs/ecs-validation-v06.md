# ECS 对比验证与 v0.6 接入结果

日期：2026-10-29。结论：本轮采用 **Flecs 4.1.6**；EnTT 在随机访问、标签变更和本测试的层级访问中更快，Flecs 在批量更新和生成／销毁负载中更快。选择同时考虑查询与系统基础设施，不能解释为 Flecs 在所有负载中领先。

## 版本与工具链

- Windows x64，Intel Core i9-14900K（24 核／32 逻辑处理器），MSVC 19.39，C++20，Release `/O2`，单线程。
- Flecs 4.1.6：编译、执行通过。最终配置仅启用核心、C++ 接口、System、Pipeline 和 OS API 实现；不包含 Flecs 自带脚本、JSON、HTTP／REST 等模块。以下测量使用此配置，与引擎构建一致。
- EnTT 4.0.0：当前工具链编译失败，启用 `/permissive- /Zc:__cplusplus` 后仍有依赖类型名称及概念约束错误。没有修改第三方源码。保留 [原始编译日志](benchmarks/ecs/entt-4-msvc-19.39.log)。这只是本机版本组合的结果，不代表 EnTT 4.0 在所有 MSVC 版本上不可用。
- 性能对照实际使用 EnTT 3.16.0，避免将旧版本的测量误报成 4.0。

依赖来源：[Flecs 4.1.6](https://github.com/SanderMertens/flecs/releases/tag/v4.1.6)、[EnTT 4.0.0](https://github.com/skypjack/entt/releases/tag/v4.0.0)、[EnTT 3.16.0](https://github.com/skypjack/entt/releases/tag/v3.16.0)。下载脚本固定版本，源码 SHA-256 记录在 [依赖说明](../THIRD_PARTY.md)。

## 测量结果

下面是每轮操作的中位耗时，单位 ms；数字越小越好。

| 负载 | 1 万实体 Flecs | 1 万实体 EnTT | 10 万实体 Flecs | 10 万实体 EnTT |
| --- | ---: | ---: | ---: | ---: |
| 位置＋速度更新 | 0.0036 | 0.0062 | 0.0369 | 0.0615 |
| 随机读取位置 | 0.0679 | 0.0328 | 1.2206 | 0.4213 |
| 10% 实体添加后移除标签 | 0.0732 | 0.0260 | 0.7351 | 0.2621 |
| 生成后销毁额外 10% 实体 | 0.0980 | 0.1512 | 0.9934 | 1.5614 |
| 父先子后的层级计算 | 0.0931 | 0.0411 | 0.9624 | 0.4184 |
| 32 种组件组合下的位置更新 | 0.0042 | 0.0062 | 0.0377 | 0.0632 |

10 万实体的进程峰值工作集约为 Flecs **19.79 MiB**、EnTT **15.02 MiB**，峰值提交量约为 **16.92 MiB**、**11.33 MiB**。这包含程序、容器及测试开销，是整个进程的峰值，**不是逐组件内存统计或分配次数**。

10 万实体初次加载单次耗时为 Flecs 16.350 ms、EnTT 6.059 ms。这里使用逐实体构建，包含组件注册／查询或 Group 建立，没有采用各库最佳的批量加载策略；该行不能代表引擎最终场景加载能力，也没有多次加载的 P95／P99。

原始数据涵盖 1 千、1 万、10 万实体。每项预热 10 次，记录后续 100 次的中位数、P95 和 P99：[Flecs 10 万](benchmarks/ecs/flecs-100000.csv)、[EnTT 10 万](benchmarks/ecs/entt-100000.csv)、[全部数据](benchmarks/ecs)。

精简模块前的初轮结果单独保留在 [default-addons](benchmarks/ecs/default-addons)，不与最终配置混用。微小耗时差异可能来自测量波动，不能据此声称模块裁剪提升了 ECS 更新速度。

### 公平性与适用范围

Flecs 使用持久缓存查询，EnTT 使用拥有 Position／Velocity 的 Group，而非仅使用未经优化的临时 View。两边执行相同数值计算，移动结果和生命周期有断言，所有负载输出校验值；同规模的校验值一致。

层级测试两边均使用父索引组件，并按拓扑顺序计算；包含临时结果数组的分配。它对比的是这种访问方式，**没有直接比较 Flecs 内置 ChildOf 与 Parent 的优劣**。标签变化在 Flecs 中使用延迟合并，在 EnTT 中使用直接增删，因此测量的是各自实际可用路径，包含相应维护成本。

该测试没有 GPU、图片解码、物理、脚本 VM 或多线程任务图，也未锁定 CPU 核心和频率。桌面上的微秒级差异会受调度影响。Android／iOS／macOS／Web 尚未实测；不能把以上数字换算成完整游戏 FPS，更不能作为对 Unity、Unreal 的整体性能排名。

复现：

```powershell
./scripts/benchmark-ecs.ps1
```

实现见 [ecs_bench.cpp](../tests/perf/ecs_bench.cpp)。需要更换编译器评估 EnTT 4.0 时，应使用单独构建目录，并对两个库使用相同工具链重新运行。

## 接入后的运行结构

发布 Player 链接 Flecs、类型化场景、独立 UI 运行时和 bgfx，不链接作者文档、JSON 或图片解码器。场景源文件由 `gm_scenec` 校验和编译；组件字段按明确的二进制编码组织，纹理去重后嵌入，HUD 也编译后嵌入。运行时没有逐帧读取 JSON。

目前实现六种组件：Transform2D、Velocity、SpriteRenderer、Health、PlayerController、DamageZone。Inspector 和 CLI 使用同一套组件字段元数据与事务；类型化编译映射由 C++ 实现。运行逻辑包括输入、批量移动、父子变换、示例危险区域、渲染提取和 HUD 更新。

已采取的成本控制：

- 裁剪未使用的 Flecs 模块，Release Player 从 2,321,920 字节降到 1,843,712 字节，减少约 20.6%；不包含场景资源大小。
- 持久 ECS 查询，不逐帧建立查询或按字符串查组件。
- 渲染列表在构建时排序，稳定场景逐帧只更新已分配的行。
- HUD 对比生命值变化，值不变时不生成文字、不触发布局更新；文字只在显示的整数改变时更新。
- 场景撤销存储 JSON 差量，最多 128 步并设置 16 MiB 记录预算，避免长期保存整场景快照。
- 运行、停止时明确销毁 World 和 GPU 图片资源；编辑 World 状态与运行状态隔离。
- 暂停或后台编辑器不持续请求游戏重绘；重新激活时限制单步时间，避免位置大跳。

当前仍使用简单的父先子后变换计算，运行时场景组件组合固定；大规模动态结构变更的公共 API、增量 Transform 更新、并行调度、脚本 VM 和完整资源 GUID 数据库不属于本次已实现能力。图片在作者文件中继续使用相对路径，编译后转为索引。组件版本目前只接受 v1，不假装已有通用迁移系统。
