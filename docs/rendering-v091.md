# GM Engine 0.9.1：2D 渲染优化与验证

本轮针对当前的 2D 游戏、合作建造和游戏 UI，落实可观测性、提前剔除、纹理共享、静态几何复用、文本与位置插值。公开 SDK 仍为 **ABI 10**，资源二进制格式不变；已有 0.9.0 游戏模块可以继续使用，发布游戏需要重新打包以带上新 Player。

## 已实现

| 部分 | 当前行为 | 边界与取舍 |
| --- | --- | --- |
| 渲染诊断 | 每帧记录前端 CPU、`bgfx::frame` 提交/等待、渲染线程、GPU 时间、绘制次数、上传量、纹理及几何缓存占用；编辑器性能面板与 CLI 读取相同数据 | GPU 结果异步返回，用 `gpuFrame` 标明；不支持的指标返回 `null`。提交等待不能等同于 GPU 绘制耗时 |
| 大场景筛选 | 256 世界单位的空间网格；先查询相机覆盖区域，再处理候选精灵。排序保留原始透明绘制顺序 | 超大物体单列；巨大视口退回有界的全量扫描。旋转相机采用保守 AABB，候选不等于最终可见像素 |
| 增量维护 | 变换、尺寸、图像、颜色、UV、排序变化更新索引和 64 行一组的版本号；恢复、生成、销毁时重建对应结构 | ECS 渲染数据提取仍遍历精灵；本轮没有将整个模拟流程变成增量或并行 |
| 图片共享 | Renderer 内按 SHA-256 内容和尺寸去重，场景、HUD、预制体和编辑器图片共用引用计数；相同内容重新载入不再上传 | 哈希在获取图片时计算，不在每帧计算；仍有加载时 CPU 成本。不同 Renderer 不共享 GPU 句柄 |
| 小图集 | 最长边不超过 254 像素的图片自动进入 512×512 RGBA 图集，一像素边缘扩展防止线性采样串色；UV 区域、contain/cover、裁剪仍有效 | 当前为运行时上传阶段装填，未做离线全局装箱、mipmap 或平台压缩 |
| 静态场景缓存 | 大场景将可见的连续静态对象记录成 GPU 顶点/索引缓冲，世界坐标保持不变，相机矩阵交给 Shader；移动对象保持原顺序插入 | 小于 128 个精灵的场景沿用轻量路径；每个视图最多 64 段静态缓存。脏块会使所属可见绘制段重建，并非只上传一个脏块 |
| 静态 UI 缓存 | 同一视口和内容稳定四帧后复用 GPU 几何；内容、布局、资源、位置、视口变化均失效 | 动态 Canvas 仍每帧生成；频繁改变的 HUD 不强行建立短命缓冲 |
| 文本 | 稳定 UI 复用整个绘制缓存；动态混合文字减少一次重复的文本查找；数字继续复用原有字形图集 | 没有声称完成通用字体 shaping、双向文本、SDF/MSDF 字体系统 |
| 位置插值 | 固定模拟步之间，精灵和相机的平移使用前后两次状态插值；可见性包含插值路径；暂停、手动单步、直接修改显示当前状态 | 会有标准的一步显示延迟；旋转、缩放、缩放倍率尚不插值；不修改碰撞、网络或存档中的真实模拟位置 |

新的 `src/shaders/vs_2d.sc` 使用 `u_modelViewProj`，替换只读 `u_viewProj` 的 UI 顶点 Shader。仓库包含由固定版本 bgfx 编译的 D3D11 / OpenGLES 二进制头文件，普通构建与新建项目不依赖 Shader 编译器。修改 Shader 后运行 `scripts/build-shaders.ps1`，输出仍写回这些头文件；编译工具位于外部构建目录。

## 缓存生命周期

- 图片 GPU 分配上限 192 MiB；最多 32 张小图页，共 32 MiB，按需分配而非预占。最多 4096 个逻辑图片条目。
- 引用归零后保留 120 帧，以便场景切换复用；达到限制时提前回收。共享页仍有活动图片时只回收闲置条目，整页在完全闲置后销毁。空洞暂不搬移，避免使现有 UV 失效。
- 静态几何上限 32 MiB；闲置 600 帧的缓存可在后续录制时回收，视图销毁/切换主动释放。容量或 GPU 缓冲句柄不足时回退到普通绘制。
- 图片和文字物理纹理销毁会使相关版本的几何缓存失效，避免缓存引用已释放 GPU 资源。目前用全局纹理版本保守失效，未来可细分依赖。
- 保持原绘制顺序，不通过跨越透明物体的纹理排序降低 draw call。缓存可能增加少量绘制次数，目的是减少 CPU 重建和上传。

## 如何查看

在编辑器运行场景，打开右侧“性能”标签。统计包含整个编辑器 Renderer 的已完成帧，不能误认为只有游戏视图的成本；精灵可见性计数来自场景视图。

通过既有会话连接查询：

```powershell
'{"op":"runtime.render.stats"}' | & D:/Demo/GMEngineApp/bin/gmctl.exe --live <会话目录>
```

无图形的 `gmctl --project ... --stdio` 返回 `available:false`，不会制造 GPU 数字。`gm_scene_capture` 在截图旁额外输出 `截图.png.stats.json`，适合游戏项目的自动回归。

`frontendMs` 包含 `Renderer::begin` 到最终 flush 的 CPU 工作；`submitWaitMs` 单独记录 `bgfx::frame` 调用。`vertexUploadBytes` 包含顶点和索引，`textureUploadBytes` 包含实际 RGBA 上传及文字页初始化；驱动内部暂存、对齐、复制不在该计数内。`imageTextureBytes` / `textTextureBytes` / `geometryBytes` 是本 Renderer 管理的有效分配。`adapterMemoryUsedBytes` 是后端/驱动报告的适配器指标，可能包含其他程序，不能当作本引擎专用显存。

## 性能对比

Windows Release / D3D11，同一台 i9-14900K 机器，960×600，80 帧取后 60 帧中位数。下表测量 `view.render` 的 CPU 绘制准备，不包含模拟、最后一次 flush、提交等待和 GPU 执行；因此不是 FPS，也不是与 Unity/Godot/Unreal 的公平横向评测。

| 场景 | 0.9.0 保存的基准程序 | 0.9.1 | 绘制次数 |
| --- | ---: | ---: | ---: |
| 图片 UI | 12.3 μs | 3.4 μs | 7 → 7 |
| 300 个标签 | 84.5 μs | 2.7 μs | 2 → 2 |

上述静态 UI 暖机后纹理和顶点上传均为 0。初次建立缓存有分配和上传成本，持续变化的 UI 不会获得同样的收益。

另有 40,000 建筑场景，在同一个新测试程序内比较“全量扫描、逐个变换/裁剪”的参考路径与空间查询/缓存路径，CPU 绘制准备约 **1.22 ms → 0.015 ms**。两者经过真实 GPU 截图逐像素比对；这项参考不是旧版本完整游戏运行时间。视口包含 570 个精灵，网格只检查 768 个候选；暖帧只上传 92 字节背景几何，静态精灵复用 52,440 字节 GPU 缓冲。绘制次数从参考路径的 1 次变为 2 次。

原始测量保存在 `D:/Demo/GMEngineBuild/render-v091/`；可复现命令：

```powershell
& D:/Demo/GMEngineBuild/build/Release/gm_render_bench.exe D:/Demo/GMEngineBuild/build/fixtures/Release/ui/images.gmui
& D:/Demo/GMEngineBuild/build/Release/gm_scene_render_tests.exe D:/Demo/GMEngineBuild/render-v091/scene
& ctest --test-dir D:/Demo/GMEngineBuild/build -C Release --output-on-failure
```

## 验证范围

本轮本地验证：15 项 CTest 全部通过；模拟无 CMake 的安装验证 11 项通过（含真实编辑器与新统计接口）；CrystalMeadow 41 项实时编辑器检查通过；CoopWorkshop 三个原生进程的联机协议回归、TouchLab 输入/UI/存档回归、DSPNative 模拟及四个原生画面捕获通过。CoopWorkshop 同一初始画面的 0.9.0 / 0.9.1 PNG 文件 SHA-256 完全一致。

- SHA-256 已知向量；200 次随机空间查询与暴力扫描比对；负坐标、超大对象、更新/移除、巨大视口回退。
- 插值系数、前后位置、相机同步、旋转包围盒、暂停/单步、销毁、恢复及相同规模场景替换。
- 原生 GPU 像素对比：图集边缘采样、图片裁剪、静态 UI、4 万精灵场景、相机平移/缩放/旋转、颜色与排序变更。
- 多视图纹理共享、同内容重载零上传、单张图片变更、4200 次临时图片更换、引用释放与整页回收、UI 尺寸变化、文字缓存淘汰。
- Windows 本地运行 GPU 契约；GitHub 托管 Windows CI 跑无 GPU 的契约，排除名称匹配 `renderer_contract` 的两项测试。
- Android ARM64 已编译新的 OpenGLES Shader 与渲染代码；没有连接真机，不能据此声称完成 Android 画面和性能验证。

## 仍待完善

1. 以真实项目测量 ECS 提取/变换成本，再做脏标记、分区更新及必要的并行。当前空间查询优化的是提交前端，不是所有 System。
2. 离线图集与增量装箱、mipmap、ASTC/ETC2 等平台导入产物及目标设备对比；当前仍使用 RGBA8。
3. 通用材质/Shader 资源、RenderTexture、多相机合成、粒子和后处理；本轮只增加引擎内部 2D 顶点 Shader。
4. 字体资源、复杂文字 shaping、可缩放字形方案与更细粒度 UI 脏区缓存。
5. 3D、光照、阴影、PBR，以及 iOS/Metal、Web 等平台的完整渲染链路，不能仅因 bgfx 支持这些后端就算已完成。

本轮没有用资源缓存掩盖这些缺项，也没有把 CPU 微基准收益外推为整款游戏或所有平台的性能收益。
