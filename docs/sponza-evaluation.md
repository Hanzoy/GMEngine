# Intel Sponza 2022 大场景接入记录（2026-11-01）

先前 Lumen Sanctum 的建筑是参数化生成的，不能用来代表专业模型的细节质量。这次另建 `D:/Demo/GMEngineGame/projects/SponzaGallery`，导入 Intel 发布的真实 Sponza 2022 基础场景。原包和原始 glTF 保留在 `GMEngineGame/references/IntelSponza2022`，大型资产不进入引擎 Git 仓库。

## 来源与实际规模

- [Intel 官方下载页](https://www.intel.com/content/www/us/en/developer/topic-technology/graphics-research/samples.html)，下载入口 `https://cdrdv2.intel.com/v1/dl/getContent/830833`。
- ZIP 3,987,608,266 字节（3.714 GiB）；SHA-256 `b8bb853884ab1566b3beb35666bd09882a4e0dc16661e4684e103792cf0229b9`。
- glTF 115 个源 mesh、155 个节点、405 个材质子网格、28 个材质；3,747,018 个三角形，没有减面或用重复实例虚增统计。
- 72 张源贴图全部 4096×4096，保留原分辨率，离线生成 BC3 mipmap。另加一张 1×1 RGBA8 白色占位纹理。
- 转换几何 GPU 数据约 104.85 MiB；纹理链合计约 1536.00 MiB；编译场景约 1.60 GiB。
- 随包文件包含 CC-BY 4.0 正文，但开头另有个人、教育和有限商业用途描述。本次只作本机测试；保留全部原始许可及署名，不宣称可无条件商用。详见游戏项目的 `ATTRIBUTION.md`。

也核对了 [NVIDIA ORCA 的 Amazon Lumberyard Bistro](https://developer.nvidia.com/orca/amazon-lumberyard-bistro)，它是后续城市/室内测试候选。本轮实际下载、转换、渲染的是 Intel Sponza，不能把候选列表当作已验证资产。

## 本次实际修正

1. 原引擎构建直接报 `Render resources exceed 128 MiB`。新增 CMake `GM_RENDER_RESOURCE_BUDGET_MIB`，默认仍 128，允许 128–2048。编译器、渲染资源验证/二进制读写、同步与异步场景读取使用同一上限，场景额外留 64 MiB 给实体与 UI。安装元数据记录该值，增量导入签名包含该值，避免换回小容量构建时错误沿用缓存。
2. 本机应用和本示例 Player 使用 2048 MiB 评估构建。它只是显式扩大有界的常驻容量，不是流式加载、无限容量或生产级大型世界方案。旧安装包默认 128 MiB，不能运行这个大场景。
3. Player 以前为了计算窗口大小加载一次场景，创建运行时又加载一次。现在前一次解析的对象直接移动到运行时，省去重复文件读取与解析。
4. 首次 GPU 上传失败暴露了 1×1、仅 BC3 的占位纹理不满足当前 D3D11 上传条件。项目改用 4 字节 RGBA8 占位；真实 4K 纹理仍用 BC3。GPU 报错补上纹理索引和尺寸，方便定位资源。
5. 项目侧离线 glTF→OBJ 桥接脚本保留全部三角形，处理节点 TRS/矩阵、法线逆转置、坐标系/绕序、UV 和材质分组，按需要拆分大 mesh。全白顶点色经过检查后省略；UV1 未被该源材质引用。切线在 Shader 中用导数重建。**这不等于引擎原生 glTF 导入已经完成。**
6. 项目侧自定义 Shader 读 base color、normal、roughness(G)/metallic(B)，支持可选 occlusion / emissive。保留源材质 alpha / doubleSided 配置；不把所有表面改成单色。

## 性能测量口径

测试机 RTX 4090 D、Windows / D3D11。离屏捕获使用引擎本身的 `gm_scene_capture`，无 VSync，固定模拟 dt=1/60；稳定后采样，CPU 与延迟 GPU 样本分别统计，不将帧耗时倒数宣称为桌面实际 FPS。相机及采样参数、PNG、原始 `.benchmark.json` 和进程内存记录保存在游戏项目 `tools` / `docs`。

首次完整编译 166.74 秒，gmctl 进程峰值工作集约 6.43 GiB。该测量包括模块构建调用、资源索引、PNG 解码、mipmap、压缩、网格导入和场景写出；内存只统计 gmctl 进程，不含其子进程。不是资源冷磁盘读取基准。

完整运行/画面测量汇总见游戏项目 `docs/evaluation.json`。显存中的纹理+网格计数是引擎资源数据量；DXGI adapter memory 指标不等于本游戏独占显存。第一帧上传不能混入稳定渲染时间。

## 暴露出的下一阶段优先项

| 优先级 | 真实观察 / 限制 | 下一步 |
| --- | --- | --- |
| P0 | 场景将网格和全部纹理内嵌在单个约 1.6 GiB 文件，加载时整体常驻 | 外部共享资源包、按块读取、异步上传、预算内驻留与卸载 |
| P0 | 改一张小贴图或调整相机也会触发整场景重新转换纹理 | 每资源派生数据缓存，区分 scene / mesh / texture / shader 构建产物 |
| P0 | 编译峰值工作集约 6.43 GiB，场景序列化有大向量副本 | 流式编码/校验和、消除 bank/scene 编码中间副本 |
| P0 | 专业模型已有细节，但画面仍欠缺空间感 | 阴影、IBL、AO、间接光，之后再考虑 GI / 反射；不能把模型质量当作光照能力 |
| P1 | 仅原生 OBJ；转换后需要 405 个子网格文件 | 原生 glTF 2.0 导入、材质/纹理关联、切线/顶点色/多 UV 格式支持 |
| P1 | 有视锥裁剪，无遮挡裁剪、LOD 或网格流式；遮挡后的几何仍可能提交 | 先测遮挡收益，再实现分层 LOD/遮挡剔除 |
| P1 | 打包入口 `game.gmscene` 与 catalog 场景各有一份完整内容 | 让启动入口引用 catalog 资源，减少重复磁盘占用 |
| P1 | 只验证 Windows BC3；法线没有 BC5 专用格式 | 移动端压缩/容量策略与真机验证，BC5/BC7 和纹理质量选项 |
| P1 | 模型初次加载无进度 UI；编辑器实时预览还会走整个场景编译 | 进度/取消、后台导入、让编辑预览复用派生资源 |

不要仅靠继续提高上限来替代上述资源架构改造。100 GB 是用户允许的磁盘素材规模，不是本引擎目前可一次性常驻或流畅渲染的能力承诺。

## 回归

新增独立的 1 MiB 测试构建，验证真实资源编码器的容量边界、元数据开销、溢出保护、截断输入和往返读取，不在 CI 分配 2 GiB 来测试一个上限。现有 19 项引擎契约加此项共 20 项全部通过。项目构建、打包、真实 1080p / 4K 渲染和 Player 浏览另行实测，详见游戏项目报告。

独立项目构建/模块扩展/打包回归 15 项通过；Sponza 图像对比与资源检查 7 项通过，包括 W+Shift 移动、R 精确恢复原视角、界面隐藏、性能档降低目标尺寸与后处理次数、完整网格与纹理上传。真实桌面 Player 成功打开；自动化 F1 输入未在游戏模块观测到，因此增加并实测了 H 作为隐藏界面的备用键，不将其误报为已修复的引擎键盘缺陷。
